## User Scenarios & Testing _(mandatory)_

### User Story 1 - ユーザー登録 (Priority: P1) 🎯 MVP

新しいユーザーがメールアドレス・パスワード・氏名を送信して、文書管理システムにアカウントを作成する。

**Why this priority**: アカウントがなければログインもファイル管理もできない。認証基盤の最も基本的な機能。

**Independent Test**: 登録を実行し、ユーザー情報が返ることを確認。

**Acceptance Scenarios**:

1. **Given** 未登録のメールアドレスを使う状態で、**When** 有効な情報（email, password, name）で登録を行うと、**Then** ユーザー情報（id, email, name, createdAt）が返る
2. **Given** 登録済みのメールアドレスがある状態で、**When** 同じメールアドレスで登録を試みると、**Then** 重複エラーが返る
3. **Given** パスワードが 8 文字未満の状態で、**When** 登録を試みると、**Then** バリデーションエラーが返る

---

### User Story 2 - ログインと JWT 発行 (Priority: P1) 🎯 MVP

登録済みユーザーがメールアドレスとパスワードでログインし、JWT を取得する。

**Why this priority**: JWT がなければ Files サービスを含む他サービスの認証付きエンドポイントにアクセスできない。

**Independent Test**: ログインを実行し、JWT が返ることを確認。

**Acceptance Scenarios**:

1. **Given** 正しい認証情報を持つ状態で、**When** ログインを行うと、**Then** JWT（accessToken, tokenType, expiresIn）およびユーザー情報が返る
2. **Given** 誤ったパスワードを送信した状態で、**When** ログインを試みると、**Then** 認証エラーが返る
3. **Given** 存在しないメールアドレスで、**When** ログインを試みると、**Then** 認証エラーが返る（登録済みかどうかを推測させない）

---

### User Story 3 - JWT による認証中ユーザー取得 (Priority: P1) 🎯 MVP

クライアントが JWT を Authorization ヘッダーに付けて自身の情報を取得する。

**Why this priority**: JWT の検証エンドポイントは、Files サービスなど他サービスがユーザーを識別するための基盤となる。

**Independent Test**: 有効な JWT を用いて認証中ユーザー情報を取得し、正しい情報が返ることを確認。

**Acceptance Scenarios**:

1. **Given** 有効な JWT を持つ状態で、**When** 認証中ユーザー情報を取得すると、**Then** ユーザー情報（id, email, name）が返る
2. **Given** JWT が未指定の状態で、**When** 認証中ユーザー情報を取得しようとすると、**Then** 認証エラーが返る
3. **Given** 期限切れの JWT を持つ状態で、**When** 認証中ユーザー情報を取得しようとすると、**Then** 認証エラーが返る

---

### Edge Cases

- パスワードは bcrypt でハッシュ化して保存する
- JWT の署名アルゴリズムは RS256（非対称鍵）とし、Auth は秘密鍵で署名・公開鍵で検証する。鍵は PEM ファイルのパスを環境変数で注入する
- JWT のデフォルト有効期限は 1 時間（3600 秒）
- JWT には sub（user_id）、exp、iat クレームを含める
- メールアドレスは大文字小文字を区別しない（小文字に正規化して保存）
- ログイン失敗時に「メールアドレスが間違っている」か「パスワードが間違っている」かを区別しない（情報漏洩防止）
- パスワードの長さ制限: 最小 8 文字、最大 128 文字
- メールアドレスの長さ制限: 最大 255 文字
- 氏名の長さ制限: 最小 1 文字、最大 100 文字

## Requirements _(mandatory)_

### Functional Requirements

#### ユーザー登録

- **FR-001**: システムはメールアドレス、パスワード、氏名によるユーザー登録を受け付けなければならない
- **FR-002**: システムはパスワードを bcrypt でハッシュ化して保存しなければならない
- **FR-003**: メールアドレスが既に登録されている場合、重複エラーを返さなければならない
- **FR-004**: パスワードが 8 文字未満または 128 文字超の場合、バリデーションエラーを返さなければならない

#### ログイン

- **FR-005**: システムはメールアドレスとパスワードによるログインを受け付け、JWT を発行しなければならない
- **FR-006**: JWT は RS256（非対称鍵）で署名し、`sub`（user_id）、`exp`、`iat` クレームを含めなければならない
- **FR-007**: ログイン成功時には accessToken、tokenType（"Bearer"）、expiresIn（秒）、ユーザー情報を返さなければならない
- **FR-008**: 認証失敗時は失敗原因を特定できる情報を含めてはならない

#### 認証中ユーザー情報取得

- **FR-009**: システムは Bearer トークンとして渡された JWT を検証し、認証中ユーザーの情報を返さなければならない
- **FR-010**: JWT が未指定、無効、または期限切れの場合、認証エラーを返さなければならない

#### エラーハンドリング

- **FR-011**: エラーレスポンスは統一された形式（メッセージとエラーコードを含む）で返さなければならない

### Key Entities

- **User**: id (UUID), email (unique), passwordHash, name, createdAt, updatedAt

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: ログインのレスポンスタイムが 200ms 以内
- **SC-002**: パスワード比較は constant-time で行い、タイミング攻撃に耐性がある
- **SC-003**: 全エンドポイントが API 仕様と一致する

## Assumptions

- Auth サービスは独立したマイクロサービスとして構成する
- JWT の署名鍵（秘密鍵・公開鍵の PEM パス）およびトークン有効期限は環境変数で注入・変更可能とする
- ユーザーの役割（管理者/一般ユーザー）やパスワードリセット機能は初期スコープ外
- フロントエンド UI の実装は本仕様のスコープ外とする
