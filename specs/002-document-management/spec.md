# Feature Specification: 文書管理

**Feature Branch**: `002-document-management`
**Created**: 2026-05-07
**Status**: Draft
**Input**: 文書管理サービスのバックエンドAPI。チームで文書を共有・整理するためのファイル管理システムを Files マイクロサービスとして提供する。

---

## User Scenarios & Testing _(mandatory)_

### User Story 1 - ファイルアップロード (Priority: P1) 🎯 MVP

認証済みユーザーがファイルと説明文を送信し、システムにファイルを登録する。

**Why this priority**: ファイル管理の最も基本的な機能。ファイルをシステムに取り込めなければ何も始まらない。

**Independent Test**: ファイルをアップロードし、ファイル情報が返ることを確認。

**Acceptance Scenarios**:

1. **Given** 認証済みユーザーが有効な JWT を持つ状態で、**When** ファイルと説明文を送信すると、**Then** ファイル情報（ID、ファイル名、サイズ、MIME タイプ、ダウンロード URL）が返る
2. **Given** 10MB を超えるファイルを送信した状態で、**When** アップロードを試みると、**Then** サイズ超過エラーが返る
3. **Given** JWT が未指定の状態で、**When** アップロードを試みると、**Then** 認証エラーが返る

---

### User Story 2 - ファイル一覧取得と検索 (Priority: P1) 🎯 MVP

認証済みユーザーがファイル一覧を取得し、キーワード検索やタグフィルタで絞り込む。

**Why this priority**: アップロードしたファイルを見つけて確認できなければ管理システムとして成立しない。

**Independent Test**: ファイル一覧を取得し、ページネーション・検索・タグフィルタが機能することを確認。

**Acceptance Scenarios**:

1. **Given** ファイルが 5 件登録されている状態で、**When** ファイル一覧を取得すると、**Then** ファイル一覧（各ファイルの ID、名前、サイズ、タグ ID 一覧、アップロード日時）と総件数が返る
2. **Given** ファイルが 25 件登録されている状態で、**When** 1 ページ目を 20 件ずつで取得すると、**Then** 最初の 20 件と総件数 25 が返る
3. **Given** ファイル名に「請求書」を含むファイルがある状態で、**When** 「請求書」でキーワード検索すると、**Then** 該当するファイルのみが返る
4. **Given** 特定のタグが付いたファイルがある状態で、**When** そのタグ ID でフィルタすると、**Then** そのタグが付いたファイルのみが返る
5. **Given** 検索条件に一致するファイルがない状態で、**When** 検索を実行すると、**Then** 空の結果と総件数 0 が返る

---

### User Story 3 - ファイル詳細取得とダウンロード (Priority: P1) 🎯 MVP

認証済みユーザーがファイルの詳細情報を取得し、元のファイルをダウンロードする。

**Why this priority**: ファイルの内容確認とダウンロードは MVP に必須の基本機能。

**Independent Test**: ファイル詳細の取得とダウンロードが正しく動作することを確認。

**Acceptance Scenarios**:

1. **Given** ファイルが登録されている状態で、**When** ファイル詳細を取得すると、**Then** ファイル詳細（ID、名前、サイズ、MIME タイプ、説明、タグ ID 一覧、アップロード日時、ダウンロード URL）が返る
2. **Given** ファイルが登録されている状態で、**When** ファイルをダウンロードすると、**Then** 元のファイルのバイナリデータが返る
3. **Given** 存在しないファイル ID を指定した状態で、**When** 詳細を取得しようとすると、**Then** 存在しないエラーが返る

---

### User Story 4 - タグ管理 (Priority: P2)

認証済みユーザーがタグを作成・取得・更新・削除し、ファイルの分類に使用する。

**Why this priority**: タグはファイル整理の基本機能だが、MVP 段階ではアップロード時にタグなしでも運用可能。体系的なタグ管理は P2。

**Independent Test**: タグの作成・取得・更新・削除が正常に動作することを確認。

**Acceptance Scenarios**:

1. **Given** 認証済みユーザーが有効な JWT を持つ状態で、**When** タグ名「重要」と色「red」でタグを作成すると、**Then** タグ情報（ID、名前、色、作成日時）が返る
2. **Given** タグが登録されている状態で、**When** タグ一覧を取得すると、**Then** 全タグの一覧が返る
3. **Given** タグが登録されている状態で、**When** タグ名を変更すると、**Then** 更新されたタグ情報が返る
4. **Given** 同名のタグが既に存在する状態で、**When** 同じ名前でタグを作成しようとすると、**Then** 重複エラーが返る
5. **Given** タグが登録されている状態で、**When** タグを削除すると、**Then** タグが削除される

---

### User Story 5 - ファイルメタデータ編集 (Priority: P2)

認証済みユーザーがファイルのファイル名、説明、タグを変更する。

**Why this priority**: アップロード後のメタデータ修正は実運用で必須だが、MVP 後に実装すべき機能。

**Independent Test**: ファイル名・説明・タグを変更し、変更が反映されることを確認。

**Acceptance Scenarios**:

1. **Given** ファイルが登録されている状態で、**When** ファイル名を変更すると、**Then** 更新されたファイル情報が返る
2. **Given** ファイルが登録されている状態で、**When** タグ ID 一覧を変更すると、**Then** タグの関連が更新される
3. **Given** 存在しないファイル ID を指定した状態で、**When** 更新を試みると、**Then** 存在しないエラーが返る

---

### User Story 6 - ファイル削除 (Priority: P2)

認証済みユーザーがファイルを削除する。一括削除にも対応する。

**Why this priority**: ファイル管理において不要なファイルの削除は必須機能。一括削除により運用効率を向上させる。

**Independent Test**: ファイルの個別削除と一括削除が正しく動作することを確認。

**Acceptance Scenarios**:

1. **Given** ファイルが登録されている状態で、**When** ファイルを削除すると、**Then** ファイルが削除される
2. **Given** 複数のファイルが登録されている状態で、**When** ファイル ID 一覧を指定して一括削除すると、**Then** 指定したファイルがすべて削除される
3. **Given** 存在しないファイル ID を指定した状態で、**When** 削除を試みると、**Then** 存在しないエラーが返る

---

### Edge Cases

- 対応ファイル形式は MIME タイプで判定（PDF、Word、Excel、画像等）
- 1 ファイルあたりの最大サイズ: 10MB
- ファイル名の一意性は不要（同名ファイルは別ファイルとして登録）
- タグ名は一意制約あり（重複時は重複エラー）
- タグ色は定義済みの列挙値から選択（blue, red, yellow, green, purple, orange, gray）
- ファイル削除時にタグとの関連も同時に削除される
- タグ削除時にファイルとの関連も同時に削除される
- 不正なページネーションパラメータにはバリデーションエラーを返す

## Requirements _(mandatory)_

### Functional Requirements

#### ファイルアップロード

- **FR-001**: システムはファイルと説明文によるファイルアップロードを受け付けなければならない
- **FR-002**: ファイル（必須）と説明文（任意、最大 500 文字）を指定できなければならない
- **FR-003**: システムは 1 ファイルあたり最大 10MB の制限を適用し、超過時にサイズ超過エラーを返さなければならない

#### ファイル一覧・検索

- **FR-004**: システムはファイル一覧をページネーション付きで返さなければならない（デフォルト: 1 ページ目、20 件ずつ）
- **FR-005**: システムはファイル名の部分一致によるキーワード検索をサポートしなければならない
- **FR-006**: システムはタグ ID（複数指定可）によるフィルタをサポートしなければならない
- **FR-007**: 一覧取得のレスポンスにはファイル一覧、総件数、ページ番号、件数制限を含めなければならない

#### ファイル詳細・ダウンロード

- **FR-008**: システムはファイル ID を指定してファイルの詳細情報を返さなければならない
- **FR-009**: システムはファイル ID を指定してファイル本体をダウンロードできなければならない
- **FR-010**: 存在しないファイル ID に対して存在しないエラーを返さなければならない

#### タグ管理

- **FR-011**: システムはタグ（名前・色）を作成できなければならない
- **FR-012**: システムは全タグ一覧を取得できなければならない
- **FR-013**: システムはタグ名・色を更新できなければならない
- **FR-014**: システムはタグを削除できなければならない
- **FR-015**: タグ名は一意でなければならず、重複時に重複エラーを返さなければならない
- **FR-016**: タグ色は定義済みの列挙値（blue, red, yellow, green, purple, orange, gray）から選択しなければならない

#### ファイル編集

- **FR-017**: システムはファイル名、説明、タグ ID 一覧の変更を受け付けなければならない

#### ファイル削除

- **FR-018**: システムはファイル ID を指定してファイルを削除できなければならない
- **FR-019**: システムはファイル ID 一覧を指定した一括削除をサポートしなければならない

#### 認証・エラーハンドリング

- **FR-020**: すべてのエンドポイント（ヘルスチェックを除く）は JWT Bearer トークンで認証しなければならない
- **FR-021**: JWT が未指定または無効な場合、認証エラーを返さなければならない
- **FR-022**: エラーレスポンスは統一された形式（メッセージとエラーコードを含む）で返さなければならない
- **FR-023**: システムはヘルスチェック機能を認証なしで提供しなければならない

### Key Entities

- **File (ファイル)**: id, name, size, mimeType, description, uploadedAt, downloadUrl, tagIds
- **Tag (タグ)**: id, name, color, createdAt, updatedAt

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: ファイルアップロード（5MB）のレスポンスタイムが 5 秒以内
- **SC-002**: ファイル一覧取得のレスポンスタイムが 500ms 以内（100 件登録時）
- **SC-003**: キーワード検索のレスポンスタイムが 1 秒以内（100 件登録時）
- **SC-004**: 認証なしのリクエストはすべて拒否される
- **SC-005**: 全エンドポイントが API 仕様と一致する

## Assumptions

- 認証機能は既存の 001-user-auth を再利用する。Files サービスは受け取った JWT を検証してユーザーを識別する
- アクセス権限は全ユーザーが全ファイルを閲覧・編集・削除可能とする（個別権限は実装しない）
- ファイルストレージはストレージインターフェースで抽象化する
- Files サービスは Auth サービスとは独立したデータベースを持つ（マイクロサービス境界の原則に準拠）
- ファイルのバージョン管理は実装しない（同名ファイルは別ファイルとして登録）
- 同時アクセスユーザー数は最大 50 人を想定
- フロントエンド UI の実装は本仕様のスコープ外とする
