# Day 1 で何を書き、何を直したか

自分の手が入ったファイルと、その理由をまとめておく。後から「なぜこうなっているのか」を思い出すため。

---

## 大きな流れ

最初に `openapi.yaml` を一気に書き上げて、検証が通ったところで一度満足していた。
そのあと「この行はどこから来た数字なんだろう」と一つずつ見直したら、根拠を説明できない箇所がいくつも出てきた。
後半はその点検と手直しに使った。

結果として、**足したものより削ったもののほうが印象に残っている。**

---

## `schema/files/openapi.yaml`

今日の本体。ゼロから書いたファイル。エンドポイント 4 本とスキーマ 4 つを定義した。

### 直した箇所は 5 つ

#### 1. `sort` パラメータを丸ごと削除した

一覧取得に並び替えの機能を付けていた。ファイル名順、更新日時順、サイズ順の 6 通りから選べるようにして、
`enum` で不正な値を弾ける形にもしていた。設計としては悪くなかったと思う。

ただ、見直したら**仕様書に並び替えの要件が書かれていない**。
さらに、実際にこの API を呼ぶ側であるフロントエンドの設計図を見ても、`sort` を使っていなかった。

つまり誰も要求していない機能だった。「あったほうが便利だから」で足していた。

削除したが、代わりに `data-model.md` のほうに
「**並び順は `uploaded_at DESC` 固定。仕様に要件がないため API パラメータとしては公開しない**」
と書き残した。一覧に順序そのものは必要なので、消したのではなく内部仕様に格下げした形。

#### 2. `search` の文字数制限に理由を書いた

もともと `maxLength: 255` とだけ書いてあった。なぜ 255 なのか説明できなかったので、理由を添えた。

```yaml
maxLength: 255
description: files.name が VARCHAR(255) のため、それを超える検索語は一致し得ない
```

数字自体は変えていない。**根拠を明示しただけ**だが、これで「なんとなく」ではなくなった。

#### 3. アップロードで受け付けるファイル形式を指定した

仕様書の Edge Cases に「対応ファイル形式は MIME タイプで判定（PDF、Word、Excel、画像等）」とあるのに、
設計図には何も書いていなかった。

最初はレスポンスの `mimeType` を `enum` で 5 種類に限定しようとしたが、途中でやめた。
仕様書に「画像**等**」と書いてあるからで、返す側を閉じた列挙にすると仕様より厳しくなってしまう。
将来対応形式が増えたときに、レスポンスの形を変えることになるのも避けたかった。

そこで、本当に縛りたい**アップロード側だけ**に指定を入れた。

```yaml
encoding:
  file:
    contentType: >-
      application/pdf,
      application/vnd.openxmlformats-officedocument.wordprocessingml.document,
      application/vnd.openxmlformats-officedocument.spreadsheetml.sheet,
      image/jpeg,
      image/png
```

#### 4. `FileInfo` に制約と説明を足した

レスポンスで返すファイル情報に、制約がほとんど書かれていなかった。
フロントエンド側の設計図と見比べたら**あちらのほうが丁寧**で、負けていることに気づいた。

| 項目 | 足したもの | 根拠 |
| --- | --- | --- |
| `name` | `minLength: 1` / 説明 | DB の `files.name VARCHAR(255)` |
| `size` | `minimum: 1` / `maximum: 10485760` | 仕様書 FR-003「1 ファイル最大 10MB」 |
| `mimeType` | `maxLength: 255` / 説明 | DB の `mime_type VARCHAR(255)` |

`10485760` は 10 × 1024 × 1024。説明文にも「上限 10MB（FR-003）」と書いて、
後から読む人が計算し直さなくて済むようにした。

#### 5. `FileListResponse` に下限を足した

こちらも制約が抜けていた。

- `total` に `minimum: 0` — 検索結果が 0 件になる場合があるため
- `page` に `minimum: 1` — ページ番号は 1 始まり
- `limit` に `minimum: 1` / `maximum: 100` — リクエスト側と同じ範囲に揃えた

リクエストのパラメータには制限を書いていたのに、レスポンスには書いていなかった。
**入口だけ厳しくて出口が緩い**状態だったので、対称にした。

### 直さなかったこと

`/files/{fileId}/content` というダウンロードの URL は、そのままにした。

フロントエンド側は `/download` を呼ぶ設計になっていて、このままだと繋がらない。
それでも変えなかったのは、`content` のほうが REST の原則（URL は名詞、動作は HTTP メソッド）に沿っているから。

黙って合わせるより、**食い違いを見つけたことを報告するほうが価値がある**と判断した。
実際に繋ぐ段階になったら、どちらに寄せるかを相談すればいい。

## `specs/002-document-management/data-model.md`

`/speckit.plan` が生成したファイル。**1 箇所だけ手で直した。**

`sort` を OpenAPI から消したとき、こちらには `Sort SortField` という記述が残っていた。
片方だけ直すと、次に読む人が「API に無いのに設計書にはある」と混乱する。

削除ではなく、経緯が分かる形に書き換えた。

> **並び順は `uploaded_at DESC` 固定**（内部仕様）。`spec.md` にソートの機能要件が存在しないため、
> API パラメータとしては公開しない。一覧に安定した順序は必要なので、実装側で新しい順に固定する。
> ソート機能が要求された時点で `sort` クエリパラメータと `SortField` 型を追加する。

**「なぜ無いのか」が分かる状態**にしておきたかった。

## `docs/MY-DAY1-GUIDE.md`

自分用の作業メモとして新しく作ったファイル。

前半は調べたことの記録。リポジトリを読んで分かった「もう決まっていること」をまとめた。
エラーの形は Auth サービスで確定済み、401 の中身は共有ミドルウェアがハードコードしている、
`/healthz` は憲法の例外規定で OpenAPI に書かない、など。

後半は空の表を用意して、そこを埋めていく形にした。

- エンドポイントの一覧表
- 機能要件（FR）とエンドポイントの対応表
- スキーマの設計
- 自分で決める必要がある論点と、その判断・理由

**FR の対応表が特に効いた。** 空欄が残る＝エンドポイントか項目が足りない、という形で
抜け漏れが目に見えるようになる。

## 触っていないもの

意識的に手を出さなかったファイル。

| ファイル | 理由 |
| --- | --- |
| `services/files/api/gen/server.gen.go` | 自動生成物。直しても次の生成で消える |
| `schema/auth/openapi.yaml` | Auth サービスはお手本。読むだけ |
| `packages/authjwt/` | 共有ライブラリ。実装済み |
| `docs/day1-design.md` | 進行資料。誤りは見つけたが、勝手に直さず報告する |

`day1-design.md` については、優先度の表がフロントエンド版からのコピーで
このリポジトリの仕様書と食い違っていた。資料どおりに進めていたら、
必須機能（ファイル詳細取得とダウンロード）を作らずに終わっていた。

## 振り返って

設計そのものより、**「なぜそう書いたか」を言える状態にする作業**に時間がかかった。

数字を一つ書くにも、仕様書のどこから来たのか、データベースの定義と合っているのかを確かめる必要がある。
逆に言えば、それを確かめずに書いた行は後から必ず説明できなくなる。

`sort` を削除したのは象徴的だった。**動くものを作るなら、あって困る機能ではない。**
それでも仕様駆動で進めている以上、「便利そう」は理由にならない。
