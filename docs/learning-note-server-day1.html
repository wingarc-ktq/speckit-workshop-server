学習ノート

OpenAPI ってなに？
作る前に「約束」を決める

サーバーのコードを書く前に、まず設計図を書く。その設計図が OpenAPI。

そもそも何をしたのか

サーバー（画面の裏で動くプログラム）を作るとき、いきなりコードを書き始めません。先に「どんな窓口を用意するか」を決めた文書を書きます。それが openapi.yaml です。

今回作ったのは、文書管理システムのサーバー側。用意した窓口は4つです。

やりたいこと用意した窓口
ファイルをアップロードするPOST /files
ファイル一覧を見る・検索するGET /files
1件の詳細情報を見るGET /files/{fileId}
ファイル本体をダウンロードするGET /files/{fileId}/content

この4つについて、「何を受け取って、何を返すか」を細かく書いたのが今回の成果物です。

イメージをつかむ

🛠建物の設計図みたいなもの

家を建てるとき、いきなり木材を切る大工はいません。まず図面を描きます。

図面があると、大工・電気屋・水道屋が相談しなくても同じ家を作れます。「コンセントはここ」と図面に書いてあるからです。

施主の要望
「3LDK で日当たりのいい家」		 → spec.md（仕様書）
「ファイルを保存して検索できるようにしたい」
図面
寸法がミリ単位で決まっている		 → openapi.yaml
受け取る値・返す値が決まっている
実際の工事 → プログラムを書く作業

工事が始まってから「やっぱり間取りを変えたい」となると壁を壊すことになります。先に図面を固めるのは遠回りに見えて近道です。

📄そして「契約書」でもある

もうひとつの顔があります。API は 画面を作る人とサーバーを作る人の約束でもあります。

「こういう名前で呼んだら、こういう形で返す」と決めておけば、お互いの完成を待たずに並行して作れます。

約束がズレていると繋がらない

実際に、前に作った画面と今回のサーバーを比べたらこうなっていました。

  • 画面が呼ぶのは /files/{id}/download
  • サーバーが待っているのは /files/{id}/content

繋いだ瞬間に「そんな窓口はありません」（404 エラー）になります。どちらが間違いという話ではなく、すり合わせていなかったのが問題です。

🧱設計図からプログラムの枠が生成される

コンクリートを流すには型枠が要ります。手作りだと寸法が狂いますが、図面から機械で切り出せば必ず図面どおりになります。

これを実行すると、

make gen-oapi

設計図から 「4つの窓口に対応する関数の枠」 が自動で作られます。中身は空っぽで、後から埋めます。

func ... GetFiles(ctx echo.Context) error
func ... UploadFile(ctx echo.Context) error
func ... GetFile(ctx echo.Context) error
func ... DownloadFileContent(ctx echo.Context) error
設計図と中身がズレようがない

手で関数を書いていたら、設計図を直したとき実装を直し忘れます。生成なら設計図を直してコマンドを回すだけ。これが「OpenAPI ファースト」と呼ばれる考え方です。

実際の中身を読んでみる

いちばん単純な「ファイル詳細を取得する窓口」です。1行ずつ意味があります。

schema/files/openapi.yaml 
  /files/{fileId}:            # URL。{fileId} は可変（呼ぶ側が値を入れる）
    get:                      # get = 取得する
      summary: ファイル詳細取得   # 短い説明
      operationId: getFile     # ★ここが生成される関数名になる★
      parameters:
        - name: fileId
          in: path            # URL の中に埋め込む値、という意味
          required: true      # パスの一部なので必ず要る
          schema:
            type: string
            format: uuid      # UUID 形式
      responses:
        "200":                # 成功したとき
          description: 取得成功
          content:
            application/json:  # JSON で返す
              schema:
                $ref: "#/components/schemas/FileResponse"   # 別の場所に書いた定義を参照
        "404":                # ファイルが無かったとき
          description: ファイルが存在しない
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/ErrorResponse"

$ref は「別の場所に書いた定義を使い回す」記号です。同じ形を何度も書かずに済みます。参照される側を先に書く必要があるので、定義 → 窓口の順で書きました。

数字には根拠がいる

制約を書くとき、「なんとなく」の数字を書かないのが大事でした。

schema/files/openapi.yaml 
        name:
          maxLength: 255       # 根拠: データベースの列が VARCHAR(255) だから

        size:
          minimum: 1            # 0バイトのファイルは登録させない
          maximum: 10485760     # 根拠: 仕様書の「最大10MB」= 10 × 1024 × 1024

説明文に根拠を書いておくと、後から読む人が「なぜ 255 なんだろう」と悩まずに済みます。

わかったこと

資料より仕様書が正しい

進行の説明資料にあった「作るものの一覧」が、別の教材からのコピーになっていて、優先度の番号がずれていました。資料では「後回し」とされていた機能が、仕様書では最優先でした。

説明資料と仕様書が食い違ったら、仕様書が正。そのまま信じていたら必須機能をひとつ作り忘れていました。

自由に決められる範囲は思ったより狭い

設計を始める前に既存のコードを読んだら、すでに答えが出ている項目がたくさんありました。エラーの返し方、認証失敗時のメッセージ、書式のルール。

ゼロから考える前に「すでに決まっていることを探す」。そのぶん、本当に自分で決めるべきところに集中できます。

「便利そう」は理由にならない

並び替えの機能を追加していました。あったほうが便利だと思ったからです。

でも見直したら仕様書に並び替えの要件がなく、使う側の画面も呼んでいませんでした。誰も要求していない機能だったので削除しました。

設計図に書く1行1行には出典（どこから引いてきたか）が必要で、「あったほうがいい」は出典になりません。

正しく作っても繋がらないことがある

ダウンロードの URL を /content にしたのは、REST という設計の原則に沿った判断でした。URL は名詞にして、動作は GET / POST などで表す、という考え方です。

でも既存の画面は /download を呼んでいました。API は正しさの競争ではなく合意だと分かりました。

関連する文書は一緒に直す

並び替えを削除したとき、データ設計のほうにその記述が残っていました。片方だけ直すと次に読む人が混乱します。

今回は消すのではなく「並び順は新しい順で固定。理由はこれ」と書き換えたので、なぜ無いのかが分かる状態になりました。

小さく作って、小さく確かめる

設計図を全部書いてから検証すると、エラーが出たときどこが原因か分かりません。窓口をひとつ書くたびに検証コマンドを回すと、直前に足した部分が原因だと即座に分かります。
