SECTION 02直感的な補足

家を建てるとき、いきなり木材を切り始める大工はいません。まず図面を描きます。

図面があると何が起きるか。大工・電気屋・水道屋が、お互いに相談しなくても同じ家を作れます。「コンセントはここ」「水道管はここ」が図面に書いてあるからです。

今日 1 日かけて図面だけ描いたのは、遠回りに見えて近道だからです。工事が始まってから「やっぱり間取りを変えたい」となると、壁を壊すことになります。

📄OpenAPI ＝ 2 社間の契約書

もう 1 つの顔があります。API は「画面を作る人」と「サーバーを作る人」の間の契約書でもあります。

「こういう名前で呼んだら、こういう形で返します」という約束です。約束があるから、お互いの完成を待たずに並行して作れます。

今日、実際に契約違反が見つかりました

昨日作った画面は、ファイルのダウンロードを /files/{id}/download という名前で呼びます。
今日私が設計したサーバーは、/files/{id}/content という名前で待っています。

繋いだ瞬間に「そんな窓口はありません」（404 エラー）になります。どちらが間違っているという話ではなく、約束をすり合わせていなかったのが問題です。

サーバー編の初日資料には、こう書いてありました。

APIの安定性: 使う相手（他サービス・フロント・外部）を把握しきれない。壊すと本番で一斉に動かなくなる

🧱コード生成 ＝ 図面から型枠を起こす

コンクリートを流し込むには「型枠」が要ります。型枠を手作りすると寸法が狂いますが、図面から機械で切り出せば必ず図面どおりになります。

今日実行したこのコマンドが、それをやっています。

cd services/files
make gen-oapi   # openapi.yaml → Go のコードを自動生成

生成されたのは 「4 つの API に対応する関数の枠」です。中身は空っぽで、Day 2 で埋めます。

func (w *ServerInterfaceWrapper) GetFiles(ctx echo.Context) error
func (w *ServerInterfaceWrapper) UploadFile(ctx echo.Context) error
func (w *ServerInterfaceWrapper) GetFile(ctx echo.Context) error
func (w *ServerInterfaceWrapper) DownloadFileContent(ctx echo.Context) error
設計図と実装がズレようがない

手で関数を書いていたら、設計図を直したときに実装を直し忘れます。生成なら、設計図を直して make gen-oapi を回すだけ。ズレる余地がありません。これが「OpenAPI ファースト」と呼ばれる考え方です。

🧾出典のある設計 ＝ 根拠のある見積書

リフォームの見積書に「その他工事 15 万円」とだけ書いてあったら不安になりますよね。金額には根拠が要ります。

OpenAPI も同じで、書いてある 1 行 1 行に「なぜそう書いたか」の出典があるべきです。今日の後半は、その点検をしました。

SECTION 03重要なコード

1. API を 1 つ定義する

いちばん単純な「ファイル詳細を取得する API」です。1 行ずつ意味があります。

schema/files/openapi.yaml 
  /files/{fileId}:            # URL。{fileId} の部分は可変（呼ぶ側が値を入れる）
    get:                      # HTTP メソッド。get = 取得する
      summary: ファイル詳細取得   # 一覧に出る短い説明。憲法で必須
      operationId: getFile     # ★生成される Go の関数名になる★ キャメルケースの動詞句
      tags:
        - files               # ドキュメント上のグループ分け
      parameters:
        - name: fileId
          in: path            # URL の中に埋め込む値、という意味
          required: true      # パスの一部なので必ず要る
          schema:
            type: string
            format: uuid      # UUID 形式。Auth サービスの User.id に合わせた
      responses:
        "200":                # 成功したとき
          description: 取得成功
          content:
            application/json:  # JSON で返す
              schema:
                $ref: "#/components/schemas/FileResponse"   # 後述の定義を参照
              example:         # ★憲法で必須★ 実際に返る値の見本
                file:
                  id: "3fa85f64-5717-4562-b3fc-2c963f66afa6"
                  name: "田中商事_請求書.pdf"
        "404":                # ファイルが無かったとき
          description: ファイルが存在しない
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/ErrorResponse"
              example:
                message: "ファイルが見つかりません"
                code: "FILE_NOT_FOUND"
$ref は「別の場所に書いた定義を参照する」記号

同じ形を何度も書かずに済みます。FileResponse の中身を直せば、参照している全箇所に反映されます。だから定義を先に書き、参照する側を後に書く必要がありました。

2. 制約に根拠を持たせる

見直しで直した部分です。数字にすべて出典があります。

schema/files/openapi.yaml 
    FileInfo:
      properties:
        name:
          type: string
          minLength: 1
          maxLength: 255       # 出典: data-model.md の files.name VARCHAR(255)
          description: 元のファイル名（DB 定義 files.name VARCHAR(255) に対応）

        size:
          type: integer
          format: int64
          minimum: 1            # 0 バイトのファイルは登録させない
          maximum: 10485760     # 出典: FR-003「1ファイル最大 10MB」= 10 × 1024 × 1024
          description: ファイルサイズ（バイト）。上限 10MB（FR-003）

description に出典を書いておくのがポイントです。半年後の自分や他の人が「なぜ 255 なんだろう」と悩まずに済みます。

3. アップロードできる形式を縛る

仕様書の「対応ファイル形式は MIME タイプで判定（PDF、Word、Excel、画像等）」を、OpenAPI で表現した部分です。

schema/files/openapi.yaml 
      requestBody:
        content:
          multipart/form-data:      # ファイルを送るときの形式
            schema:
              type: object
              required:
                - file              # ファイルは必須（FR-002）
              properties:
                file:
                  type: string
                  format: binary    # ファイルの中身そのもの、という意味
                description:
                  type: string
                  maxLength: 500    # 出典: FR-002「説明文は最大 500 文字」
            encoding:               # ★どの形式のファイルを受け付けるかの指定★
              file:
                contentType: >-
                  application/pdf,
                  application/vnd...wordprocessingml.document,   # Word
                  application/vnd...spreadsheetml.sheet,         # Excel
                  image/jpeg,
                  image/png
なぜ「返す側」ではなく「受け取る側」を縛ったのか

最初は返すデータのほうに「この 5 種類しかあり得ない」と書こうとしました。でも仕様書には「PDF、Word、Excel、画像等」と書いてあります。「等」がある以上、5 種類に閉じるのは仕様より厳しすぎます。

本当に縛りたいのは「受け付ける形式」なので、アップロード側だけに書きました。将来対応形式が増えても、返す側の約束を壊さずに済みます。

SECTION 04今日の学び

つまずき資料の説明が仕様書と食い違っていた

今日の進行資料（day1-design.md）にある「作るものの一覧表」が、昨日のフロントエンド版からのコピーで、ストーリー番号がずれていました。

資料では「ファイル詳細は後回し（P2）」となっていましたが、実際の仕様書では最優先（P1）でした。資料を信じていたら、必須機能を 1 つ作り忘れるところでした。

教訓：説明資料と仕様書が食い違ったら、仕様書が正。昨日 E2E テストで学んだ「ドキュメントより実物」と同じ構図です。

気づき自分で決めていいことと、決まっていることがある

設計を始める前に既存のコードを読んだら、すでに答えが出ている項目がいくつもありました。

  • エラーの形（message と code の 2 つ）→ Auth サービスで確定済み
  • 「認証されていません」のエラー内容 → 共有プログラムが固定文言を返す
  • /healthz は設計図に書かない → 憲法に例外規定あり

教訓：ゼロから考える前に、すでに決まっていることを探す。自由に決められる範囲は思ったより狭く、その分だけ判断に集中できます。

つまずき「便利そう」で機能を足していた

並び替え（sort）のパラメータを追加していました。あったほうが便利だと思ったからです。

でも見直したら、仕様書に並び替えの要件がありません。さらに、実際に使う側であるフロントエンドも並び替えを呼んでいませんでした。誰も要求していない機能だったので削除しました。

教訓：仕様駆動開発では「あったほうがいい」は理由になりません。ただし完全に消したのではなく、「並び順は新しい順で固定（内部仕様）」と文書に残しました。一覧に順序は必要だからです。

気づきフロントと繋ぐと壊れることが分かった

昨日作った画面の設計図と、今日作ったサーバーの設計図を並べて比べました。

  • ダウンロードの URL が違う（/download vs /content）→ 繋ぐと 404
  • フロントはタグ機能の API を呼ぶが、サーバー側には存在しない → タグが表示されない
  • ID の形式が違う（file_abc123 形式 vs UUID）

教訓：片方だけ「正しく」設計しても繋がりません。API は合意であって、正しさの競争ではない。これが「契約書」と呼ばれる理由を実感しました。

気づき設計図と設計書がズレることもある

sort を削除したとき、data-model.md（データ設計書）のほうに Sort の記述が残っていました。片方だけ直すと、次に読む人が混乱します。

教訓：関連する文書は一緒に直す。今回は「削除」ではなく「並び順は固定、理由はこれ」と書き換えたので、なぜ無いのかが分かる状態になりました。

気づき1 本ずつ書いて、そのつど検証する

設計図を全部書いてから検証すると、エラーが出たときにどこが原因か分かりません。1 つの API を書くごとに make gen-oapi を回すと、直前に足した部分が原因だと即座に分かります。

教訓：これはプログラミング全般に言えることです。小さく作って、小さく確かめる。
