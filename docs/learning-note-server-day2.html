設計図から
動くサーバーを作る

前回書いた openapi.yaml をもとに、実際に動くプログラムを組み立てた。

そもそも何をしたのか

前回は「どんな窓口を用意するか」を紙の上で決めた。今回はその窓口の向こう側で実際に働くプログラムを書いた。

できあがったものはこう動く。

# ファイルをアップロードする
curl -X POST http://localhost:8082/api/v1/files \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@請求書.pdf"

# → 201 Created
# {"file":{"id":"3fa85f64-...","name":"請求書.pdf","size":204800, ...}}

前回 openapi.yaml に「こう返します」と書いた形が、本当にその形で返ってきた。

イメージをつかむ

🍴4 つの層 ＝ 飲食店の役割分担

プログラムを 4 つの層に分けて書いた。これは飲食店の役割分担に近い。

handler（ホール係） お客さんの注文を聞いて、できた料理を運ぶ。厨房のことは知らない
▼
usecase（料理人） 実際に作る。「10MB を超えていたら断る」などのルールを持つ
▼
infra（仕入れ・倉庫係） データベースやファイル保存とやりとりする

この分け方の何が嬉しいか。ホール係は「食材がどこから来たか」を知らなくていいし、料理人は「注文がスマホから来たか電話から来たか」を知らなくていい。

実際に効いた場面

最初の計画では、料理人（usecase）が「アップロードされたデータの塊」を直接開ける想定だった。でもそのデータは巻き戻せない形式で、順番を間違えると読めなくなる。

そこでデータを開けて仕分ける仕事はホール係（handler）に移した。料理人は「読めるもの」を受け取るだけ。結果的に、料理人が通信の形式を知らずに済むようになり、層の分け方としても正しくなった。

🔌最後の工程は「配線工事」

4 つの層はそれぞれ完成していて、テストも全部通っていた。それでもサーバーは起動しなかった。

部品はできているが、繋がっていなかったからだ。家でいうと、部屋は全部できたけど配線工事がまだで、スイッチを押しても照明が点かない状態。

最後の工程で、こういうことを書いた。

  • 8082 番ポートで待ち受ける
  • /files にリクエストが来たら handler を呼ぶ
  • handler は usecase を使う、usecase は DB とストレージを使う
  • 認証チェックを全部の窓口に掛ける（ただし死活監視は除く）

この「誰が誰を使うか」を組み立てる作業を DI（依存性注入） と呼ぶ。プログラムの中で一番最後に書く部分で、ここだけが全部の層を知っている。

🎭テストには 2 種類ある

今回、性格の違うテストを 2 つ書いた。

単体テスト統合テスト
相手 偽物（モック） 本物の PostgreSQL
速さ 一瞬 数十秒（コンテナ起動）
分かること ロジックが正しいか SQL が本当に動くか

モックは「台本どおりに答える代役」だと思えばいい。「この ID で聞かれたら、このデータを返してね」と決めておく。相手が代役なので、DB が無くてもテストできるし一瞬で終わる。

ただし代役は台本どおりにしか動かないので、「SQL の書き方が本当に正しいか」は分からない。そこは本物の PostgreSQL を立てて確かめた。テストのたびに使い捨てのコンテナが起動して、終わったら消える。

実際のコードを読んでみる

層をまたぐときにエラーを翻訳する

internal/infra/repo/file_repository.go 
// SQL がヒットしない場合、sqlc 生成コードは pgx.ErrNoRows を返す。
// これはあくまで pgx（DB ドライバ）が使う内部的なエラー型であり、
// usecase/handler 層に漏れ出すと DB の詳細に依存してしまう。
// そのため、ここで domain.ErrFileNotFound に変換してから返す
// （出典: spec.md FR-010）
if errors.Is(err, pgx.ErrNoRows) {
    return nil, domain.ErrFileNotFound
}

pgx.ErrNoRows は「PostgreSQL 用のライブラリが使うエラー」。これをそのまま上の層に渡すと、もし将来 MySQL に変えたら、上の層まで全部書き直しになる。

ここで自分たちの言葉（ErrFileNotFound）に翻訳しておけば、DB を変えても書き直すのはこの 1 箇所だけで済む。

死活監視だけ認証を外す

internal/server/server.go 
// /healthz・/readyz には JWT ミドルウェアを掛けない。
// なぜなら:
//   1. この2つは Docker/Kubernetes 等のインフラが定期的に叩く「死活監視」用で、
//      呼び出し元はオーケストレーター（人間ではない）であり JWT を持っていない。
//      認証必須にすると、ヘルスチェック自体が失敗して正常なコンテナが
//      再起動され続ける、という本末転倒な事態になる。
//   2. 仕様上も「認証なしで提供しなければならない」と明記されている
//      （出典: spec.md FR-023）
e.GET("/healthz", healthHandler.Live)
e.GET("/readyz", healthHandler.Ready)

「認証を掛けない」という判断にも理由がいる。掛け忘れたのか、意図的に外したのかが、コメントで区別できる。

わかったこと

部品が全部正しくても、繋ぐと壊れることがある

4 つの層それぞれのテストは全部通っていた。統合テストも本物の DB で通っていた。それでも、実際にサーバーとして起動したら全リクエストがエラーになった。

原因は前回書いた設計図の 1 行。「アップロードできるファイル形式」の書き方が、検証を担当するライブラリに正しく解釈されなかった。OpenAPI の仕様上は正しい書き方だったが、ライブラリが対応していなかった。

各部品のテストは「部品が正しいか」しか見ていない。「設計図がライブラリに正しく伝わるか」は、繋いで動かすまで誰も確かめていなかった。

入力ミスと故障は別物

最初の実装では、想定外のエラーが起きたとき一律で「あなたの送ったデータが悪い」（400）と返していた。

でもデータベースが落ちているときにこれを返すと、利用者は「入力を直せば通る」と思って何度も試すことになる。本当はサーバー側の問題（500）なのに。

既知のエラー（ファイルが無い、サイズ超過）だけをここで扱い、それ以外は素通しする形に直した。

「閉じない」という判断にも理由がいる

ファイルをダウンロードするとき、読み取り用に開いたものをあえて閉じずに次に渡している。

レスポンスを書き終わるまで開いたままにする必要があり、途中で閉じると読めなくなるから。しかも自動生成されたコードが最後に閉じてくれるので、こちらで閉じると二重に閉じてしまう。

「やらない」ことにも理由を書かないと、後から見た人が「閉じ忘れでは？」と直してしまう。

テストが見ていない隙間がある

一覧取得に、ページ番号が範囲外のとき総件数が 0 になるバグが残っている。ファイルが 3 件あるのに 99 ページ目を要求すると、「全 0 件」と返ってしまう。

統合テストには「検索して 0 件」のケースがあったが、これは本当に 0 件なので通る。「ページが範囲外で 0 件（でも総数は 3）」とは別物だった。

似て見えるケースを 1 つで済ませると、隙間ができる。

手元で動くのに Docker で壊れる問題

Go には複数のプロジェクトをまとめて扱う仕組みがある。手元ではその仕組みのおかげで、別プロジェクトの設定を借りてビルドが通ってしまうことがある。

でも Docker の中では 1 つのプロジェクト単体でビルドするので、借りていた設定が無くなって失敗する。

今回は毎回両方のモードでビルドを確認していたので早めに気づけた。「手元では動く」は証明にならない。

自動生成は「枠」だけ

設計図から生成されたのは、関数の名前と型と入力チェックだけ。中身は空っぽだった。

今回埋めたのはその中身で、生成が肩代わりしてくれるのは「間違えやすい単純作業」の部分だと実感した。設計図と実装がズレる心配がなくなるのが一番の効果。
