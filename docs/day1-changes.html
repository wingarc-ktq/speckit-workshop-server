作業記録 / サーバー編 Day 1

何を書き、何を直したか

後から「なぜこうなっているのか」を思い出すための記録。

大きな流れ

最初に openapi.yaml を一気に書き上げて、検証が通ったところで一度満足していた。

そのあと「この行はどこから来た数字なんだろう」と一つずつ見直したら、根拠を説明できない箇所がいくつも出てきた。後半はその点検と手直しに使った。

結果として、足したものより削ったもののほうが印象に残っている。

schema/files/openapi.yaml

openapi.yaml 今日の本体。ゼロから書いた。エンドポイント 4 本とスキーマ 4 つ

削除1. sort パラメータを丸ごと消した

一覧取得に並び替えの機能を付けていた。ファイル名順、更新日時順、サイズ順の 6 通りから選べるようにして、enum で不正な値を弾ける形にもしていた。設計としては悪くなかったと思う。

ただ、見直したら仕様書に並び替えの要件が書かれていない。さらに、実際にこの API を呼ぶ側であるフロントエンドの設計図を見ても、sort を使っていなかった。

つまり誰も要求していない機能だった。「あったほうが便利だから」で足していた。

- - name: sort
-   schema:
-     enum: [name, -name, uploadedAt, -uploadedAt, size, -size]
-     default: -uploadedAt

削除したが、代わりに data-model.md のほうに「並び順は uploaded_at DESC 固定。仕様に要件がないため API パラメータとしては公開しない」と書き残した。一覧に順序そのものは必要なので、消したのではなく内部仕様に格下げした形。

追記2. search の文字数制限に理由を書いた

もともと maxLength: 255 とだけ書いてあった。なぜ 255 なのか説明できなかったので、理由を添えた。

  maxLength: 255
+ description: files.name が VARCHAR(255) のため、それを超える検索語は一致し得ない

数字自体は変えていない。根拠を明示しただけだが、これで「なんとなく」ではなくなった。

新設3. アップロードで受け付けるファイル形式を指定した

仕様書の Edge Cases に「対応ファイル形式は MIME タイプで判定（PDF、Word、Excel、画像等）」とあるのに、設計図には何も書いていなかった。

最初はレスポンスの mimeType を enum で 5 種類に限定しようとしたが、途中でやめた。仕様書に「画像等」と書いてあるからで、返す側を閉じた列挙にすると仕様より厳しくなってしまう。将来対応形式が増えたときに、レスポンスの形を変えることになるのも避けたかった。

そこで、本当に縛りたいアップロード側だけに指定を入れた。

+ encoding:
+   file:
+     contentType: >-
+       application/pdf,
+       application/vnd...wordprocessingml.document,
+       application/vnd...spreadsheetml.sheet,
+       image/jpeg,
+       image/png

追記4. FileInfo に制約と説明を足した

レスポンスで返すファイル情報に、制約がほとんど書かれていなかった。フロントエンド側の設計図と見比べたらあちらのほうが丁寧で、負けていることに気づいた。

項目足したもの根拠
nameminLength: 1 / 説明DB の files.name VARCHAR(255)
sizeminimum: 1 / maximum: 10485760仕様書 FR-003「1 ファイル最大 10MB」
mimeTypemaxLength: 255 / 説明DB の mime_type VARCHAR(255)

10485760 は 10 × 1024 × 1024。説明文にも「上限 10MB（FR-003）」と書いて、後から読む人が計算し直さなくて済むようにした。

追記5. FileListResponse に下限を足した

  total:
+   minimum: 0       # 検索結果が 0 件になる場合があるため
  page:
+   minimum: 1       # ページ番号は 1 始まり
  limit:
+   minimum: 1
+   maximum: 100     # リクエスト側と同じ範囲に揃えた

リクエストのパラメータには制限を書いていたのに、レスポンスには書いていなかった。入口だけ厳しくて出口が緩い状態だったので、対称にした。

直さなかったこと

/files/{fileId}/content というダウンロードの URL は、そのままにした。

フロントエンド側は /download を呼ぶ設計になっていて、このままだと繋がらない。それでも変えなかったのは、content のほうが REST の原則（URL は名詞、動作は HTTP メソッド）に沿っているから。

黙って合わせるより、食い違いを見つけたことを報告するほうが価値があると判断した。実際に繋ぐ段階になったら、どちらに寄せるかを相談すればいい。

その他に触ったファイル

data-model.md /speckit.plan が生成したファイル。1 箇所だけ手で直した

sort を OpenAPI から消したとき、こちらには Sort SortField という記述が残っていた。片方だけ直すと、次に読む人が「API に無いのに設計書にはある」と混乱する。

削除ではなく、経緯が分かる形に書き換えた。

並び順は uploaded_at DESC 固定（内部仕様）。spec.md にソートの機能要件が存在しないため、API パラメータとしては公開しない。一覧に安定した順序は必要なので、実装側で新しい順に固定する。ソート機能が要求された時点で sort クエリパラメータと SortField 型を追加する。

「なぜ無いのか」が分かる状態にしておきたかった。

MY-DAY1-GUIDE.md 自分用の作業メモとして新しく作った

前半は調べたことの記録。リポジトリを読んで分かった「もう決まっていること」をまとめた。エラーの形は Auth サービスで確定済み、401 の中身は共有ミドルウェアがハードコードしている、/healthz は憲法の例外規定で OpenAPI に書かない、など。

後半は空の表を用意して、そこを埋めていく形にした。

  • エンドポイントの一覧表
  • 機能要件（FR）とエンドポイントの対応表
  • スキーマの設計
  • 自分で決める必要がある論点と、その判断・理由
FR の対応表が特に効いた

空欄が残る＝エンドポイントか項目が足りない、という形で抜け漏れが目に見えるようになる。

意識的に手を出さなかったファイル。

ファイル理由

day1-design.md については、優先度の表がフロントエンド版からのコピーでこのリポジトリの仕様書と食い違っていた。資料どおりに進めていたら、必須機能（ファイル詳細取得とダウンロード）を作らずに終わっていた。

振り返って

設計そのものより、「なぜそう書いたか」を言える状態にする作業に時間がかかった。

数字を一つ書くにも、仕様書のどこから来たのか、データベースの定義と合っているのかを確かめる必要がある。逆に言えば、それを確かめずに書いた行は後から必ず説明できなくなる。

sort を削除したのは象徴的だった。動くものを作るなら、あって困る機能ではない。それでも仕様駆動で進めている以上、「便利そう」は理由にならない。
